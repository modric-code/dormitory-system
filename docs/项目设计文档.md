# A02 校园宿舍综合管理系统 —— 项目设计文档

## 1. 需求分析

### 1.1 功能性需求
1. 用户管理：管理员、学生两种角色，登录、注册、退出，角色权限隔离。
2. 学生管理：学生信息（学号、姓名、性别、学院、专业、班级、电话）的增删改查与多条件查询。
3. 宿舍楼管理：楼栋（名称、楼层数、类型、宿管员）的增删改查。
4. 房间管理：房间（所属楼栋、房间号、楼层、床位数、性别、状态）的增删改查与多条件查询。
5. 入住管理：为学生办理入住分配房间、退宿，实时更新房间入住人数与状态。
6. 调宿管理：学生从一个房间调往另一房间，记录原房间、新房间、原因、经办人。
7. 维修管理：学生提交报修申请，管理员受理并更新维修进度与状态。
8. 查询功能：学生/房间/工单支持按关键字、状态、类型等多条件组合查询。
9. 数据统计：宿舍入住率（各楼栋及总体）、维修工单按状态/类型统计。

### 1.2 非功能性需求
- 易用性：Bootstrap 简洁界面，操作直观，全程中文。
- 性能：SQLite 文件数据库，单机数据量下响应快速。
- 安全性：密码加密存储（Django 内置），角色权限控制，CSRF 防护。
- 可维护性：代码模块化，命名清晰，注释完整。
- 兼容性：只需 Python 环境，无需安装数据库服务。

## 2. 系统总体设计

### 2.1 系统架构（Django MVT 三层架构）
浏览器 → URL 路由(URLconf) → 视图(View 业务逻辑) → 模型(Model 数据) → SQLite
                           ↘ 模板(Template 页面) ↖

### 2.2 模块划分（模块结构图文字描述）
系统
├── 用户模块（登录 / 注册 / 退出 / 权限）
├── 学生管理模块（增删改查 + 多条件查询）
├── 宿舍管理模块
│   ├── 宿舍楼管理（增删改查）
│   └── 房间管理（增删改查 + 多条件查询）
├── 入住管理模块（入住分配 / 退宿）
├── 调宿管理模块（调宿登记 / 记录查询）
├── 维修管理模块（报修申请 / 进度处理 / 多条件查询）
└── 数据统计模块（入住率统计 / 工单统计）

## 3. 数据库设计

### 3.1 E-R 图文字描述
实体（共 7 个）：用户、学生、宿舍楼、房间、入住记录、调宿记录、维修工单。

关系：
- 用户(1) —— (0..1) 学生  （一对一：一个账号关联一个学生档案）
- 宿舍楼(1) —— (N) 房间   （一对多：一栋楼含多个房间）
- 学生(1) —— (N) 入住记录 （一对多：一个学生可有多条历史入住记录）
- 房间(1) —— (N) 入住记录 （一对多：一个房间可容纳多个入住）
- 学生(1) —— (N) 调宿记录 （一对多）
- 房间(1) —— (N) 调宿记录 （一对多，原房间/新房间两个外键）
- 学生(1) —— (N) 维修工单 （一对多）
- 房间(1) —— (N) 维修工单 （一对多）

### 3.2 数据表结构

【dormitory_user 用户表】
- id 主键自增；username 用户名；password 密码(加密)；role 角色(admin/student)；phone 电话；is_staff/is_superuser 等 Django 内置字段。

【dormitory_dormitory 宿舍楼表】
- id 主键；name 楼栋名称(唯一)；floors 楼层数(int)；gender 楼栋类型；manager 宿管员；note 备注；created_at 创建时间。

【dormitory_room 房间表】
- id 主键；dormitory_id 外键→宿舍楼；room_no 房间号；floor 楼层(int)；bed_count 床位数(int)；gender 性别；status 状态(空闲/已满/维修中)；note 备注。

【dormitory_student 学生表】
- id 主键；user_id 外键→用户(一对一,可空)；student_no 学号(唯一)；name 姓名；gender 性别；college 学院；major 专业；class_name 班级；phone 电话；status 住宿状态(未入住/在住)；created_at。

【dormitory_checkin 入住记录表】
- id 主键；student_id 外键→学生；room_id 外键→房间；bed_no 床位号；checkin_date 入住日期；checkout_date 退宿日期；status 状态(在住/已退宿)；note 备注。

【dormitory_transferrecord 调宿记录表】
- id 主键；student_id 外键→学生；from_room_id 外键→房间(原)；to_room_id 外键→房间(新)；reason 原因；transfer_date 调宿日期；operator 经办人。

【dormitory_repairrequest 维修工单表】
- id 主键；room_id 外键→房间；applicant_id 外键→学生；repair_type 报修类型(水电/家具/门窗/网络/其他)；description 描述；status 状态(待处理/处理中/已完成/已驳回)；apply_date 报修日期；handler 处理人；progress 进度说明；finish_date 完成日期；created_at。

## 4. 详细设计（各模块业务流程）

### 4.1 用户登录/注册
- 注册：填写用户名、密码、学号、姓名等 → 校验学号唯一 → 创建用户(角色=学生) + 学生档案 → 登录。
- 登录：校验账号密码 → 成功进入工作台，按角色显示不同菜单。

### 4.2 学生管理
- 添加：填学生信息，可同时创建登录账号；编辑：修改信息；删除：确认后删除；查询：按学号/姓名/专业/班级/状态模糊匹配。

### 4.3 宿舍楼/房间管理
- 楼栋增删改查；房间增删改查，删除楼栋会级联删除房间。房间查询按楼栋/楼层/状态/房号。

### 4.4 入住管理
- 办理入住：选学生+房间+床位 → 校验（学生无在住、房间非维修、未满员）→ 写入住记录(在住)、更新学生状态、重算房间状态。
- 退宿：将记录置为已退宿、写退宿日期、更新学生与房间状态。

### 4.5 调宿管理
- 选学生+目标房间 → 校验存在在住记录且目标不同 → 记录原/新房间 → 更新入住记录到新房间 → 重算两房间状态。

### 4.6 维修管理
- 学生报修：自动带入学生与当前房间，填类型与描述 → 生成工单(待处理)。
- 管理员处理：查看详情，更新状态/处理人/进度，完成时记录完成日期。

### 4.7 数据统计
- 统计各楼栋总床位、已住、入住率，总体入住率；工单按状态、类型计数。

## 6. 项目总结与心得
本项目基于 Django + SQLite + Bootstrap 实现了校园宿舍综合管理，覆盖入住、分配、调宿、维修、查询、统计等核心业务，采用自定义用户模型实现管理员/学生两种角色权限，通过外键与级联关系保证数据一致。开发过程加深了对 Django MVT 架构、ORM、模板渲染、表单处理与权限控制的理解，也体会到需求拆分、模块化设计对可维护性的重要性。
